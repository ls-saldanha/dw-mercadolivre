## 0. How to use this PRD

This document is a contract. You (Claude Code) implement what's in scope. You do NOT implement anything in §10 "Out of scope (v2)." If you think something out-of-scope is needed, **stop and ask the human** instead of adding it.

The human is **learning Python and SQL alongside this project.** They are not a fluent programmer. Your job is:

1. **Write the code yourself.** Don't ask them to write SQL or Python from scratch.
2. **Explain deeply as you write.** They want to understand language concepts (context managers, list comprehensions, CTEs, joins, etc.), not just project-level decisions. Teach as you go.
3. **Don't pile up new concepts.** Introduce one new idea per code block. If a snippet contains a list comp, a context manager, and a generator, slow down and explain each.
4. **At conceptually new moments only**, pause and ask the human to predict what code will do before you run it (active recall). Not on every line — only on inflection points (first dbt model, first S3 call, first time we use a join, first time we use jinja in dbt).
5. **Don't give homework exercises.** The human prefers to keep moving and ask when curious. Compensate by being more thorough in explanations and by revisiting earlier code when patterns repeat ("remember how we used a context manager for the S3 client? Same pattern here.").

Each milestone has an explicit "Stop here" line. When you hit it, stop and wait for the human to verify before continuing.

## 1. Project goal

Build a Data Warehouse that ingests synthetic internal sales data and real Brazilian central bank FX rates, transforms them through a Medallion architecture (Bronze → Silver → Gold), and exposes a sales dashboard with FX-converted revenue through a self-service interactive tool.

**Success criteria for v1.1:**

- A single command (`python run_pipeline.py`) runs the whole pipeline end-to-end without errors.
- All dbt tests pass.
- The Streamlit dashboard displays revenue trends in both BRL and USD.
- The repo is public, has a clean README with screenshots, and dbt-generated docs are published to GitHub Pages.
- The human can explain every line of code in the repo to an interviewer (with notes is fine; reading off the screen is not).

**Non-goals for v1.1:** orchestration, multiple data marts, OAuth APIs, BI servers, CI on PRs. All deferred to v2.

## 3. Data sources (v1.1)

### 3.1 Bacen PTAX (real, public, no auth)

- **Endpoint:** `https://olinda.bcb.gov.br/olinda/servico/PTAX/versao/v1/odata/CotacaoDolarDia(dataCotacao=@dataCotacao)?@dataCotacao='{MM-DD-YYYY}'&$format=json`
- **Auth:** None
- **Volume:** One row per business day
- **Purpose:** USD/BRL FX rate enrichment in the Gold layer
- **Note:** Returns no data on weekends/holidays. Silver layer forward-fills from the most recent business day.

### 3.2 Synthetic sales generator (internal, controlled)

- Python script generates fake sales, customers, and products consistent with the schema below.
- Uses `Faker` for names/addresses and `numpy.random` (fixed seed in dev mode for reproducibility).
- Generates **incremental** daily files — only "new" sales for that day, not a full refresh.
- **Volume:** ~200 sales/day, drawn from a fixed catalog of ~50 SKUs and ~200 customers.

### 3.3 Why these two and not Mercado Livre

We originally planned to use the Mercado Livre API as the primary source. It was cut from v1.1 because OAuth + rate-limit handling + response validation is three new tools at once. v2 adds it. See ADR-0009.

## 4. Data model

### 4.1 Bronze (raw, append-only)

S3 layout:
```
s3://{bucket}/bronze/
  bacen_ptax/        ingestion_date=YYYY-MM-DD/ptax.parquet
  internal_sales/    ingestion_date=YYYY-MM-DD/sales.parquet
  internal_customers/ ingestion_date=YYYY-MM-DD/customers.parquet
  internal_products/  ingestion_date=YYYY-MM-DD/products.parquet
```

Bronze tables in Postgres mirror the S3 files with one extra column: `_ingested_at TIMESTAMPTZ`.

### 4.2 Silver (typed, conformed)

Four models (we'll write them one at a time, with deep explanation of dbt concepts):

- `stg_bacen_ptax` — typed, forward-filled FX rate
- `stg_sales` — typed, deduplicated, with `order_id` as unique key
- `stg_customers` — typed, snake_case columns
- `stg_products` — typed, with derived `price_tier` (cheap/mid/premium)

### 4.3 Gold (one business mart)

- `mart_sales` — one row per `(date, product_category)`. Columns: revenue_brl, revenue_usd, order_count, units_sold, avg_order_value_brl, rolling 7d revenue. FX conversion uses the Silver PTAX table.

**Why only one mart:** v1.1 is about getting the *pattern* right end-to-end, not about coverage. v2 adds `mart_pricing` (which needs Mercado Livre) and `mart_customers` (RFM segmentation).

### 4.4 Test coverage (minimum)

For each Silver model:
- `not_null` and `unique` on primary key
- `relationships` test where there's a foreign key reference

For Gold:
- `not_null` on revenue columns
- One singular test asserting "revenue_brl is always non-negative"

## 5. Pipeline execution

A single Python script: `run_pipeline.py` at repo root. When run, it:

1. Calls the synthetic generator (writes Parquet to S3, appends today's data)
2. Calls the Bacen fetcher (writes Parquet to S3)
3. Calls the S3 → Postgres Bronze loader (idempotent on `ingestion_date`)
4. Runs `dbt build` (which is `dbt run` + `dbt test`)
5. Prints a summary: rows loaded per source, tests passed, total runtime

No scheduling, no retries, no Prefect. If something fails, you re-run it manually after fixing. This is intentional — v1.1 isolates the "build a working pipeline" lesson from the "orchestrate a pipeline" lesson.

## 7. Milestones

Each milestone has acceptance criteria. **Do not move to the next milestone until the human confirms acceptance criteria met.**

### Milestone 1 — Foundation

- Initialize repo, virtualenv (uv), `pyproject.toml`, `.gitignore`.
- Set up Supabase project; create schemas `bronze`, `silver`, `gold`.
- Create S3 bucket with the prefix layout from §4.1.
- Set up `.env` from `.env.example` with all credentials.
- Install `pre-commit` hooks (gitleaks + hygiene).
- Smoke test: a single Python script reads `.env`, connects to Supabase, writes a 1-row test Parquet to S3, reads it back, inserts a row to a `bronze.smoke_test` table, queries it.

**Acceptance:** smoke script runs green from a clean checkout.
**Stop here.**

### Milestone 2 — Synthetic generator

- Build the synthetic data generator in `ingestion/synthetic/generator.py`.
- Static catalogs (categories, names) live in `seed_data.py`.
- Output: three Parquet files per day (sales, customers, products), written to S3 Bronze partition.

Key teaching moments here: how Python modules work, what `Faker` does, what `pandas` DataFrames are, how Parquet differs from CSV, how partitioning works.

**Acceptance:** running `python -m ingestion.synthetic.generator` writes today's three files to S3. Re-running on the same day overwrites idempotently.
**Stop here.**

### Milestone 3 — Bacen fetcher

- Build the PTAX fetcher in `ingestion/bacen/fetch.py`.
- HTTP GET to the PTAX endpoint, parse the JSON response with `pydantic`, write Parquet to S3.
- Handle the weekend/holiday case: if no data, write an empty Parquet with the same schema (Silver layer will forward-fill).

Key teaching moments: what an HTTP request is, what `httpx` does, what Pydantic is for and why we validate API responses, what a context manager (`with httpx.Client() as client:`) does.

**Acceptance:** running `python -m ingestion.bacen.fetch` writes today's PTAX file to S3.
**Stop here.**

### Milestone 4 — S3 → Postgres Bronze loader

- Build `ingestion/common/loader.py` that reads Parquet from S3 and writes to Bronze tables in Postgres.
- Idempotent on `ingestion_date` — re-running overwrites that date's data, doesn't duplicate.
- Adds the `_ingested_at TIMESTAMPTZ` column on load.

Key teaching moments: what SQLAlchemy is, what an upsert/merge is, what idempotency means in pipelines.

**Acceptance:** after running ingestion + loader, Postgres has Bronze tables populated with today's data.
**Stop here.**

### Milestone 5 — dbt setup + Silver models

- Initialize dbt project. Configure `profiles.yml` for Postgres/Supabase.
- Verify `dbt debug` passes.
- Write Silver models **one at a time**, starting with `stg_bacen_ptax` (simplest). For each model: `.sql` file, `.yml` schema with tests, run `dbt build --select model_name`, verify it exists in `silver` schema with passing tests.

Claude Code writes all four models. For the *first* one, teach deeply: what dbt is doing, what `ref()` and `source()` are, what `{{ config() }}` means, what CTEs are, what a `not_null` test is. For models 2–4, narrate at the level "we're following the same pattern, here are the parts that differ."

**Acceptance:** all 4 Silver models exist in the `silver` schema, all tests pass.
**Stop here.**

### Milestone 6 — dbt Gold mart

- Write `mart_sales` joining the four Silver models. Include FX conversion (multiply revenue by PTAX rate to get USD).
- One singular test asserting non-negative revenue.

Key teaching moments: SQL joins, window functions for rolling windows, jinja templating in dbt.

**Acceptance:** `mart_sales` exists in `gold` schema, tests pass, a `SELECT * FROM gold.mart_sales LIMIT 10` shows business-sensible numbers.
**Stop here.**

### Milestone 7 — Streamlit dashboard

- Build `dashboard/app.py` that reads from `gold.mart_sales` and shows:
  - Daily revenue line chart (BRL and USD on dual axes)
  - Category breakdown (bar chart)
  - 7-day rolling average overlay

Key teaching moments: what Streamlit is, what makes a dashboard "interactive," how to connect a Python script to a database.

**Acceptance:** `streamlit run dashboard/app.py` opens a local dashboard showing the data.

### Milestone 8 — Entrypoint + docs + post

- Wire everything together into `run_pipeline.py` at repo root.
- `dbt docs generate` and publish to GitHub Pages.
- Write README with: pitch paragraph, architecture diagram, setup steps, screenshots of dashboard + dbt lineage.
- Write the post.

**Acceptance:** stranger could clone the repo, follow the README, and have it running in 30 minutes (with their own credentials).

## 8. Coding standards

- **Python:** PEP 8, type hints on function signatures, docstrings per PEP 257 on public functions. `httpx` not `requests`. Pydantic v2 for API response models.
- **SQL (dbt):** Lowercase keywords. CTEs over subqueries. One CTE per logical step. Final `SELECT` at the bottom, no `SELECT *` in final selects.
- **Naming:** `snake_case` everywhere. Bronze: `bronze.{source}_{entity}`. Silver: `stg_{source}_{entity}`. Gold: `mart_{domain}`.
- **Secrets:** `.env` locally only. Never in code or committed config.
- **Commits:** Conventional Commits (`feat:`, `fix:`, `docs:`, `chore:`). One concern per commit. The human can author commit messages or ask Claude Code to suggest one.

## 9. Guardrails for Claude Code

1. **Explain language concepts when introducing them.** Lists, dicts, comprehensions, context managers, decorators, type hints, async — all of these are new to the human. Don't skip past them.
2. **One concept at a time when possible.** If a function uses three new ideas, break the explanation into three parts.
3. **Repeat patterns when they recur.** "Same context manager pattern as the S3 client" reinforces learning.
4. **Active recall checkpoints** — at conceptually new moments (first dbt model, first SQL join, first S3 call), ask the human to predict what the code will do before running it. Not on every block — only at inflection points.
5. **Never assume the human will write code.** They are reading and understanding, not authoring. Don't ask them to "fill in the blank" or "try writing this yourself."
6. **No homework exercises.** Don't propose "now you try modifying X." The human chose to skip this.
7. **Never silently install dependencies.** Propose with reasoning, wait for approval.
8. **Out-of-scope requests** (anything in §10): respond "That's in v2. Want to add it to v1.1 scope, or keep it for later?"
9. **If asked something you're not certain about**, say so and verify with docs rather than guess.
